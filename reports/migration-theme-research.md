# Theme Research Report: Astra + Spectra to Hugo
Date: 2026-04-01

## Executive Summary

No one has ported the Astra WordPress theme to Hugo. No Hugo theme replicates Astra's look. The conventional wisdom for WP-to-Hugo migrations is a "clean break" -- pick a new Hugo theme and migrate content only. However, this project has already taken the harder (and correct) path: extracting the actual CSS from the live WordPress site and recreating Astra+Spectra styles in a hand-rolled Hugo theme (`themes/xrnav`). This approach is sound and should be continued.

---

## Part 1: Has Anyone Ported Astra to Hugo?

**No.** Extensive searching found zero results for:
- "Astra Hugo port"
- "Astra Hugo migration"
- Any Hugo theme designed to replicate Astra

The closest Hugo themes to Astra's clean business aesthetic are Zerostatic's Serif and Hero themes, but neither share Astra's class naming, layout system, or Spectra block structure.

### What People Actually Do

Every WordPress-to-Hugo migration guide recommends one of two approaches:

1. **Clean break** (most common): Export content, pick an existing Hugo theme (PaperMod, etc.), accept the visual change.
2. **Manual recreation** (rare but viable): Study the WP theme's output HTML/CSS, rebuild equivalent templates in Hugo. One practitioner (Elio Struyf) reported this was "faster than expected" using Hugo's templating engine.

This project is doing approach #2, which is the right call for visual parity.

## Part 3: Astra Architecture Analysis

### Template System (from cloned mirror)

Astra's PHP templates are minimal shells that delegate everything to action hooks:

```
header.php:  <!DOCTYPE html> → <head> → <body> → skip-link → <div id="page" class="hfeed site">
               → astra_header_before() → astra_header() → astra_header_after()
               → <div id="content" class="site-content"> → <div class="ast-container">

page.php:    get_header() → optional sidebar → <div id="primary"> → content loop → get_footer()

footer.php:  </div class="ast-container"> → </div id="content">
               → astra_footer_before() → astra_footer() → astra_footer_after()
               → </div id="page"> → wp_footer()
```

The actual header/footer HTML is generated by the Header/Footer Builder (`inc/builder/`) which reads Customizer settings and outputs components (logo, nav, buttons, widgets, etc.) into grid slots.

### CSS Generation

Astra's CSS comes from THREE sources, all generated at runtime:

1. **Static base** (`assets/css/minified/main.min.css`, 46 KB): Layout primitives, normalize, flexbox grid
2. **Dynamic inline CSS** (`<style id="astra-theme-css-inline-css">`, 67 KB): Generated by `inc/class-astra-dynamic-css.php` reading Customizer options -- contains ALL the site-specific colors, fonts, spacing, container widths
3. **Spectra inline CSS** (`<style id="uagb-style-frontend-135">`, 261 KB): Generated per-page by Spectra, one ruleset per block instance with unique IDs like `.uagb-block-0395aed3`

**Key insight**: The static CSS file is a generic framework. The visual identity lives entirely in the dynamically generated inline CSS. This is why copying `astra-main.min.css` alone would produce a generic-looking site.

### Spectra Block CSS Generation

Each Spectra block (container, heading, buttons, etc.) has a `frontend.css.php` file that:
1. Reads the block's saved attributes (colors, padding, fonts, borders, shadows)
2. Generates CSS rules scoped to `.uagb-block-{unique-id}`
3. Handles responsive breakpoints (desktop/tablet/mobile) with attribute fallbacks

The homepage alone uses 72 unique block instances generating 261 KB of CSS. This CSS is tightly coupled to the specific block IDs in the page HTML.

## Part 4: Assessment and Recommendations

### Should We Copy Astra CSS Files Directly?

**No, and the project already made the right call.** Here is why:

1. **The extracted CSS is page-specific.** The 261 KB Spectra inline CSS references 72 block IDs (`uagb-block-0395aed3`, etc.) that only exist on the homepage. Other pages generate different CSS. Copying this wholesale would mean carrying dead CSS and still missing styles for pages we did not extract from.

2. **The dynamic Astra CSS is Customizer-specific.** The 67 KB inline CSS encodes xrnavigation.io's specific Customizer choices. Useful as a reference, not as a drop-in.

3. **The Hugo site does not use WP's class structure.** Hugo templates generate different HTML. The CSS needs to target the actual Hugo markup.

**What works instead** (and what this project is already doing):
- Extract the design tokens (colors, fonts, spacing) from the WP CSS -- done, in `wordpress-compat.css` custom properties
- Recreate the visual rules targeting Hugo's actual HTML structure -- done, 2514 lines in `wordpress-compat.css`
- Use the extracted CSS as a reference/spec, not as a stylesheet -- done, in `data/wp-css/`

### Current Hugo Theme Status

The `themes/xrnav` theme already has:
- `static/css/main.css` (310 lines): Reset, focus styles, accessibility (skip link, sr-only)
- `static/css/wordpress-compat.css` (2514 lines): Full Astra+UAGB visual recreation with correct custom properties, typography, layout, header, footer, blog grid, buttons, containers
- `static/css/dark-mode.css` (158 lines): Dark mode overrides
- Templates: baseof.html, single.html, list.html, collection.html, blog templates, audiom-embed, partials for header/footer/head

### Structural Differences: WP vs Hugo

| Aspect | WordPress/Astra | Hugo/xrnav |
|--------|----------------|------------|
| Template language | PHP with action hooks | Go templates with partials |
| CSS delivery | Runtime-generated inline CSS (330+ KB) | Static CSS files (3 KB total) |
| Layout wrapper | `div.ast-container` inside `div#content.site-content` | Similar structure in baseof.html |
| Block styles | Per-instance CSS via unique block IDs | Shared classes per component type |
| Responsive | Attributes generate per-device CSS at build | Media queries in static CSS |
| Header/Footer | Built dynamically from Customizer grid slots | Static partials |
| Content | Gutenberg blocks with inline styles | Markdown + Hugo shortcodes |

The fundamental difference: WP generates unique CSS per block instance (72 blocks = 72 unique rulesets). Hugo uses shared CSS classes per component type. This is actually **better** -- the Hugo approach produces ~3 KB of CSS instead of 330+ KB, while achieving visual parity.

### What Would Make Migration Harder

1. **WP Customizer-driven layouts**: Astra's header/footer builder lets users drag components into grid slots. The Hugo site must hard-code whatever layout the WP site uses. (Already done.)
2. **Spectra block diversity**: 70+ block types, but xrnavigation.io only uses a subset (container, heading, buttons, CTA, post-grid, image, separator, info-box, forms). Only those need Hugo equivalents.
3. **Per-page Spectra CSS**: Each WP page generates different inline CSS. The Hugo approach of shared component CSS avoids this entirely.

### Recommended Next Steps

1. **Continue the current approach.** The hand-rolled CSS recreation is the right strategy. Do not switch to copying WP CSS files.
2. **Use extracted CSS as validation reference.** Compare visual output against `data/wp-css/` values when debugging discrepancies.
3. **The Astra mirror (`~/src/astra-mirror`) and Spectra source (`~/src/wp-spectra`) are available** for checking specific implementation details (breakpoints, default values, CSS generation logic) when needed.
